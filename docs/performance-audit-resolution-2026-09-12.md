## Deployment boundary

These changes remain local and uncommitted; no production deployment or remote CI run is claimed. Apply the complete migration chain before starting the updated backend. Drain and stop older API instances and their maintenance workers before starting the new API/worker on the same database: older binaries read physical files and do not honor pending durable-job visibility. Delaying only the public traffic switch is insufficient because the new worker starts before Caddy and can resume persisted jobs. Use a backend version that honors those visibility and write fences for rollback while any job remains pending or running. This verified compatibility boundary is documented in [durable tree operations](tree-operations.md).

## Measurement coverage and limits

The source audit proposes detailed acceptance profiles. The focused regressions, SQL plans and controlled comparisons establish individual mechanisms; a general HTTP gate cannot supply measurements it does not collect. These limits prevent broader performance claims; the earlier correctness and final-check failures described above have been corrected.

- PERF-003's [controlled server measurement](../performance/results/admission-2026-09-12/README.md) records same-user/other-user handler latency under provider and bulk waits. All 4,800 raw samples independently reconcile. Same-user successful-request p95 increased modestly, from 8.958 to 11.467 ms at 100 requests per second, while p99 and acceptance improved. The shared baseline rejected most provider-window requests, so successful-only percentile selection matters. The final run supports lower tails and more accepted work, not an improvement in every percentile. The [overload classification evidence](../performance/results/database-overload-2026-09-12/summary.json) separately records the actual full-queue before/after response and authenticated phase-gap tests. It does not attribute the earlier eight matrix 500 responses without their missing diagnostics, nor measure browser click-to-visible-name time or remote provider latency.
- PERF-004/006's [final API measurement](../performance/results/metadata-2026-09-12/result.json) passed all five observations and verified complete fixture cleanup. Its sampled RSS can miss peaks shorter than the ten-millisecond sampling interval; the SQL record distinguishes returned rows from internal scanned rows and buffer work. Maximum manifests use authenticated large CBOR names as a protocol-boundary fixture, not a normal UI filename. The earlier preparation-only proof remains explicitly unmeasured historical evidence. PERF-007's [release encoding result](../performance/results/metadata-2026-09-12/encoding-release.json) uses already prepared schema-sized opaque payloads, so it excludes cryptographic validation, SQL and base64 plan construction. Its byte equivalence, requested allocation volume and encode CPU observations apply to serialization only.
- PERF-005's successful 100k lifecycle measured navigation latency, process RSS and maximum batch time. The million-node crash/resume and full deletion passed. Transaction-age, WAL, vacuum and lock observations must be attributed to their specific fixture instead of inferred from request latency.
- PERF-009 has actual blocking-CPU, cancellation, revocation and concurrent setup tests. It has no attached per-Actix-worker event-loop/allocation profile for a sustained maximum-body workload.
- PERF-010/011 SQL tests cover audience semantics, moves, rollback, revisions and deferred ancestor updates. Their node/depth/fanout, WAL and sibling-lock measurements must cite the corresponding database logs. PERF-014's [dedicated realtime record](../performance/results/realtime-2026-09-12/verification-record.json) covers 1/100/2,048 in-process server subscriptions against real PostgreSQL, including 256 distinct sessions across 128 users in the largest cohort. It proves one authorization batch per cohort and bounded revocation without notifications; it does not measure 2,048 HTTP sockets or sustained whole-database QPS.
- PERF-025/026/027/036 use deterministic outage, refresh, cursor and bootstrap tests. The real browser journey adds local observations; it does not establish outage behavior across all client cohorts, networks or devices.
- PERF-018/019 have actual delayed-provider, cap and lease/failover regressions. Final mixed metrics cover the locally configured provider and maintenance workload, not production object-store rate limits.
- PERF-029/030/035's maximum-size, dependency and mixed-transfer comparisons use controlled profiles plus the real 40 MiB browser journey. The [upload profile](../performance/results/upload-pipeline-profile-2026-09-12.md) processed 2,415,919,104 generated ciphertext bytes through real scheduling/assembly/checksums, using simulated crypto/provider timing. Its 128 MiB V8 heap limit and 1 GiB device-memory hint are not physical memory limits; native RSS reached about 415 MiB. PERF-031's [download-stage comparison](../performance/results/download-stage-2026-09-12/README.md) ran 24 digest-verified transfers per runtime against the pinned serial source, plus cancellation. It uses controlled stage delays and modeled buffer accounting, not physical CPU/disk saturation or heap/RSS measurements. Chromium and Node passed; Safari remote automation was disabled and Firefox/WebKit binaries were unavailable. PERF-032/033/040's actual range recovery, prefix-byte and client timing observations are recorded in the browser evidence. They cover Chromium/OPFS with the local provider. The final pass adds a visible-text/two-frame rendering-opportunity observation and one-chunk worker count, without compositor paint or heap measurements.
