A worker-call duration includes transaction checkout, SQL work and commit, so it also bounds that call's transaction age. Every physical batch is at most 256 nodes. The 100k fixture used 784 worker calls per operation. The million-node permanent deletion used 7,816 calls, generated exactly 1,000,000 durable object cleanup jobs, and removed all operation cursor nodes. The tests assert the subtree is unavailable through direct root/descendant reads while pending, stable visible counters between physical batches, successful sibling writes, and same-owner and other-owner browsing throughout.

The test deliberately terminates a PostgreSQL backend with uncommitted cursor changes before every operation and proves those changes do not persist. For the million-node run, the first test process was also interrupted with SIGINT after 334,081 discovery rows had committed. The database job was retained and a new process resumed it with `AERALYTH_TREE_REUSE_FIXTURE=1`. The first log ends with the deliberate signal; `million-resumed.log` contains the successful completion. Its 716.47-second lifecycle and trash WAL/batch counts cover the resumed portion plus the entire subsequent deletion. They must not be interpreted as a fresh full-trash benchmark.

During the interrupted million-node discovery, EXPLAIN exposed a nullable-OR cursor predicate that repeatedly scanned earlier children and a query that reread the accumulated node table. The final worker seeks with `id > COALESCE(last_child_id, '')` and supplies its already bounded parent page via UNNEST. The before/after plans are retained in `seek-plan.log`; the empty-folder lookup in `empty-seek-plan.log` uses the parent index and four shared buffers. The resumed million run uses this corrected query. A final balanced-tree plan found 65,536 live child rows read for only 256 returned rows when 256 parents each had 256 children. The final query divides one 256-row budget among parents and advances all of their cursors. The 65,793-node balanced lifecycle passed all four operations with this refinement in `balanced-final.log`. `balanced-quota-plan.log` confirms 256 live child rows using the owner/parent index; that sample was taken during repeated state changes and includes substantial dead-version/index work before vacuum, so its 26ms timing is not a clean before/after speed comparison. PostgreSQL MVCC dead-version scans remain distinct from the logical row budget.

Queue fairness was then tested separately: two owners with 301-node trees each receive one 256-child discovery page before either receives a second.

WAL grew by 288,170,136 / 515,784,504 / 235,037,688 / 260,125,720 bytes during the final four 100k operations (113.98 seconds total lifecycle). The initial 100k run recorded 310,762,008 / 640,110,000 / 403,131,864 / 241,856,712 bytes, and 3,682,170,840 / 2,946,040,616 bytes during resumed million trash / full million delete. These values are PostgreSQL-instance WAL deltas, not per-job attribution; another isolated database workload overlapped part of the 100k run. They show that WAL remains substantial total work even though memory, locks and transaction age are bounded.
